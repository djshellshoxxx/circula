# FNET-207 upstream research and implementation handoff

Research date: 2026-11-16. **Research complete; implementation and fresh-agent audit pending. Integration HOLD remains.** No upstream source or dependency was copied/installed by this phase.

## Decision

Reuse the pure schedule parser and `Schedule.Next` API from **`github.com/robfig/cron/v3 v3.0.1`**, exact commit **`ccba498c397bb90a9c84945bbb0f7af2d72b6309`**, as a pinned dependency. It supplies mature cron/calendar calculation without introducing a mandatory service or taking authority over trades. Do not import its background runner or wrappers as a substitute for durable firing records.

This library is mature but not actively maintained: inspected default HEAD `bc59245fe10efaed9d51b56900192527ed733435` is dated 2021-01-06. That limitation must remain visible. The actively maintained GoCron and Asynq projects still depend on v3.0.1 in the versions inspected, which is evidence of continued use, not a security guarantee. The Circula adapter must add bounded inputs, explicit DST semantics and negative tests.

## Specific reuse and traps

- [Parser source](https://github.com/robfig/cron/blob/ccba498c397bb90a9c84945bbb0f7af2d72b6309/parser.go): use `cron.NewParser(cron.Minute | cron.Hour | cron.Dom | cron.Month | cron.Dow)`. `ParseStandard` enables descriptors, including `@every`; that is wider than the intended policy. A custom parser still accepts `TZ=`/`CRON_TZ=` prefixes, so do not concatenate untrusted expressions that can override the separately validated timezone.
- Prefer structured daily/weekly/monthly input, a validated IANA timezone and fixed hour/minute. Generate the five-field expression internally. If arbitrary expressions are later exposed, separately bound frequency, expression length, field count and next-occurrence search. Reject seconds, `@every`, unknown timezones and schedules exceeding the policy cap.
- [Schedule source](https://github.com/robfig/cron/blob/ccba498c397bb90a9c84945bbb0f7af2d72b6309/spec.go) and [official package documentation](https://github.com/robfig/cron/blob/ccba498c397bb90a9c84945bbb0f7af2d72b6309/doc.go): default timezone is machine-local unless explicitly configured. Spring-forward nonexistent times are skipped. `Next` is strictly after its argument; boundary tests must prevent missing an occurrence exactly at `now`. A zero result means no match was found, not an immediate firing.
- GoCron's [DST policies](https://github.com/go-co-op/gocron/blob/0caab1c6e0ecc76e1b3d2a8c2f074048e914ba39/job.go) explicitly distinguish skip from run-after-transition. Do not silently substitute its defaults for Circula's current semantics.
- Preserve current fold behavior: repeated local time produces **one** occurrence, using the first physical occurrence. A stable logical key must use network, template and local schedule window; UTC timestamps alone would permit two reminders in a DST fold. Native code must enforce this even if the upstream iterator yields both times.
- A monthly template on a missing day (e.g. February 30/31) should skip that month rather than silently shift; document and test this provisional module policy. Weekly weekdays and monthly days are bounded enum/integer inputs.
- The current `Due` performs a bounded 72-hour minute scan for every call. Replace or narrow that calculation with upstream calendar iteration plus explicit fold/gap handling; do not run a long catch-up loop over downtime. Compare behaviors with the existing DST tests before replacing it.
- Upstream job uniqueness/skip-running wrappers protect an in-memory runner, not a persisted database operation. They cannot replace a unique firing row and atomic reminder insertion.

## Current Circula seams (read only)

- `internal/service/notify.go`: `s.notify(tx store.Tx, ...)` inserts an in-app notification inside the caller's unit of work with a dedupe key. It is unexported and cannot be called directly from this independent module.
- `internal/store/sqlite_notify.go`: `InsertNotification` uses `ON CONFLICT DO NOTHING`; reminder and firing insertion need the **same** transaction. If notification insertion fails, the firing must roll back; if firing already exists, do not create another notification.
- `internal/store/sqlite.go`: `SQLite.Update` is the existing write boundary. Reuse its transaction model through a later adapter; do not open a second SQLite write transaction from inside it.
- `internal/service/transactions.go`: `ProposeTransaction` validates current actor, terms, policy, member status and idempotency before `s.propose`. A scheduled callback must never invoke proposal or acceptance automatically. A member-confirmed draft route must ultimately submit through this existing proposal flow, not a cloned ledger implementation.
- Initial standalone `Template` only contains daily time and activity booleans. Caller-provided booleans are not authorization. The full feature needs a trusted membership/policy reader rechecked in the same operation as template mutation or firing; HTTP clients must not supply trusted snapshots.

## Full isolated implementation plan

Keep all work inside `future/recurring/`; no core route, migration, workflow or configuration change now. Use independent repository/authorization/notification interfaces, a SQLite adapter for standalone tests, and explicit construction. No automatic registration or background goroutine at import.

| Scope | Implementation boundary | Required evidence |
|---|---|---|
| Template CRUD | Network + owner-scoped records: target, bounded note, optional int64 amount, recurrence, IANA zone, reminder time, active/cancelled state, revision. Validate target, current terms and limits through trusted adapter; maximum templates/member and minimum recurrence interval. | Create/read/edit/delete cross-owner/network denial; self-target/inactive/departed denial; invalid amount/text/frequency/zone; quota races; deterministic pagination. |
| Schedule semantics | Selected parser/Next adapter for daily/weekly/monthly recurrence; explicit gap-skip/fold-first and missing-month-day policies; bounded next window computation. | Exact boundaries, leap day, 30/31-day months, DST forward/back, half-hour transitions, non-DST zone, malformed/overfrequent inputs, timezone edits. |
| Durable firings | Unique `(network_id,template_id,logical_window)` with immutable occurrence key; insert firing and reminder in one transaction. Store scan progress without using it as uniqueness authority. Explicit bounded `RunDue(ctx, now, limit)` entrypoint, no auto-start. | Two workers racing yield one reminder; fail between each write and roll back; restart preserves dedupe; large downtime produces only policy-allowed recent window, no backlog storm; continuation avoids starving templates beyond first batch. |
| Pause/skip/cancel/edit | Owner-only commands with audit and concurrency revision/ETag. Persist skipped windows so restart cannot resurrect them. Editing same logical window must not create another reminder; schedule revision must not bypass dedupe. | Pause/resume/cancel/skip and edit races with firing; immutable audit; wrong-owner denial; restart after skip. |
| Fresh membership | Recheck owner and target activity and network status in firing operation; disabled/removed member suspends triggering. No hidden authority to trade. | Suspension/departure race; no proposals, acceptances or ledger writes from scheduler; no notification exposing private note/amount. |
| Manual draft | Explicit member action creates a bounded draft/prefill only; distinct stable intent per deliberate action, retries return same draft, another deliberate repeat receives a new intent. Actual proposal remains existing confirmed flow. | Retry idempotency and conflicting-payload rejection; different repeats never reuse keys; blank/optional amount behavior; fresh confirmation/terms/limits; no automatic acceptance. |
| HTTP/HTML/CLI adapters | Export opt-in handlers/CLI commands with injected trusted auth/CSRF service and no-store headers. Native forms for create/edit/pause/skip/cancel/create-draft; explain reminders never pay automatically. Proposed contracts documented locally, not registered in core. | Body bounds, CSRF, RFC9457 errors, X-Network scoping, idempotency, no-JS keyboard and accessible form tests; CLI validation/status/preview. |
| Persistence/operations | Additive feature schema isolated in adapter; indexes for owner lists and due scans; expiry/retention for templates, firings and audit; backup/restore documentation and disable procedure. | Migration from prior module schema, restore/reopen, integrity constraints, retention does not allow logical replay, no dependency on another future feature. |

The notification dependency is an interface using the existing core inbox, **not** a dependency on the unfinished email/push future module. An implementation should not claim a separately committed callback is transactionally atomic with local firing rows: the adapter must expose one shared transaction or durable outbox semantics with an honest delivery guarantee.
