# FNET-208 upstream research and implementation handoff

Research date: 2026-11-16. **Research complete; implementation and independent audit pending. Integration remains HOLD.** No upstream code or runtime dependency is added by this phase.

## Decision

Adapt the **GOV.UK Frontend radios, fieldset, error-summary and button markup/style/test patterns** into small Go `html/template` components for the no-JavaScript ballot and proposal forms. Pin the inspected source commit `a11bd3316363ab4702fcef81d6ce06a947c464ef` (package version 6.6.0), preserve its MIT license and provenance. Do not copy government branding, fonts, images or the whole Nunjucks/Sass/JavaScript application framework.

The mature governance/polling applications checked have copyleft licenses and different identity/database semantics. They are product references, **not source-code donors** for Circula's currently undecided-license codebase. Implement the small governance lifecycle and transactional ballot store in original Go using Circula's existing SQLite/service conventions. Maximizing useful reuse does not mean importing an incompatible Rails application or another application's permission model. No evaluated upstream provides a drop-in tenant-scoped, advisory-only mutual-credit governance engine.

## Existing Circula seams and gaps

- `future/governance/ballot.go` currently only validates trusted snapshots and counts ballots. Duplicate checking is an in-memory scan, not an atomic uniqueness guarantee; `Poll.Eligible` is a mutable map. There is no durable proposal lifecycle, immutable eligibility snapshot, authorization adapter, comments/moderation, process dispute, certification or HTML.
- `internal/service/principal.go`: `requireActive` excludes suspended/pending/departed members; `requireAdmin` adds active role and MFA behavior. Reuse the **existing authorization decision** through a narrow adapter, not copied role flags from HTTP input. Poll eligibility is an opening-time snapshot **and** voting still requires current active membership in the selected network.
- `internal/service/networks.go:UpdatePolicy` opens a write-scoped principal, requires admin and lasting membership, preserves notice and dual-control safeguards, and uses existing idempotency/audit. A poll majority must never bypass these guards or invoke this method automatically.
- `internal/service/gov_terms.go:PolicyLog` exposes version history. Store a separate network-scoped reference to an already authorized policy version; do not fabricate a policy version or mutate policy from a governance endpoint.
- `internal/service/announcements.go` is a reference for bounded plain text, administrator operations and service/store transactions. Its member listing permits active **and suspended** readers; do not accidentally inherit that as permission to vote.
- Root `go.mod` already selects `modernc.org/sqlite v1.60.1`, requiring Go 1.26. The isolated module may explicitly adopt the same driver/toolchain for real persistence tests; do not add another SQLite engine. Go1.26.11 is available through `/tmp/circula-toolchain/go/bin/go` with `GOTOOLCHAIN=go1.26.11`.

## Full implementation plan for a fresh agent

Work exclusively inside `future/governance/`. Do not register routes, migrations, jobs or policy hooks in the current application.

1. **Domain lifecycle and schema.** Add proposal title/context/category, author, network, open/close instants, explicit state and moderation/comment rules. Validate bounds/UTF-8 and reject invisible/control spoofing in single-line labels. Freeze eligibility and voting rules when opened; edits after opening cannot silently change the question, choices, close deadline or electorate. Keep draft edits, withdrawal reason and audit events. Use UTC instants and a server clock, not client timestamps.
2. **Durable storage.** Supply additive module-local migrations and a transaction-oriented repository over `database/sql`. Use composite network/proposal/member constraints and foreign keys; unique `(network_id, proposal_id, member_id)` ballot identity; immutable persisted snapshot and close-time outcome. Repeat a successful identical command using the same intent key; reject changed payload and duplicate fresh ballot attempts. Handle database busy/restart failures without claiming success. Never mutate a ballot to force a different result.
3. **Service authorization.** Every read/write passes a required authenticated principal/current-membership adapter and network scope. Enforce author/admin permissions for lifecycle operations, current activity plus frozen eligibility for casting, and admin authorization for certification/policy linking. The standalone test adapter is explicitly synthetic; no header becomes identity by default. Recheck authorization at the actual transactional decision boundary where possible; document the future core-store seam.
4. **Comments, moderation and process disputes.** Add bounded plain-text comments under proposal-specific rules, author deletion/hidden-view policy, moderator actions with reasons, and process-dispute records/status. No external previews, attachments or fetched URLs. Keep audit references even if content is later hidden. Separate content moderation from vote totals; do not let a moderator silently change ballots. A conflicted reviewer must not certify their own challenged action; record and test the selected conflict rule explicitly.
5. **Closure and certification.** Compute deterministic yes/no/abstain/eligible/participation counts from persisted ballots and store one immutable close result atomically. The specification defines no quorum/pass rule; present counts and **advisory** outcome rather than inventing a binding majority policy. Certification records who reviewed it and when, independently of the result and any actual policy change. Treat unresolved process disputes as an explicit certification gate rather than silently discarding them.
6. **Policy linking.** Provide a narrow read-only policy-version resolver and an authorized operation to attach a same-network, already-existing version to an outcome. Keep result, certification and applied policy separate. Never expose a callback that updates policy during tally/close/certify, never move balances, and never grant roles. Later UI links to the existing policy-change workflow, with its own authentication, MFA, notice windows and audit.
7. **Accessible presentation and adapters.** Port the selected native radio/fieldset/error patterns into `html/template`, preserving no-JS GET/POST flows, POST/Redirect/GET, fresh CSRF checks, network scope, no-store headers, body limits, escaped content, validation focus and keyboard navigation. Offer proposals, vote confirmation/receipt state, results, withdrawal, comments, disputes and admin certification/link forms. API/CLI use the same service; do not duplicate business rules in handlers. Add package API examples plus a synthetic local harness, never an automatically running server.
8. **Privacy and documentation.** Disclose server/operator/admin access to ballots and distinguish participation totals from individual choices. Ordinary member endpoints must not leak another member's ballot or enumerate eligibility identities. Export individual ballots only through explicitly authorized administrative policy, if implemented. No anonymous/coercion-resistant claim and no QuietVote dependency; future provider support is optional and deferred. Document retention, backup/restore and disable behavior before integration.

## Acceptance matrix and completion gates

| Requirement | Required evidence |
|---|---|
| Proposal content, eligibility snapshot and category | Validation/edit/open tests; immutable snapshot survives member changes and process restart; cross-network IDs rejected; no client-supplied eligibility authority |
| One eligible active member, one vote | Concurrent inserts from independent DB connections result in one ballot; same-intent retry stable; different-intent duplicate rejected; suspended/departed/late/early/wrong-network cases fail |
| Readable participation and outcome | Deterministic tally incl abstain, empty poll, ties and no invented quorum; counts agree with independent SQL fixture sum; no premature/future result mutation |
| Admin-applied policy remains separate | Spy adapter proves no policy/ledger/role write on any poll operation; forged or other-network policy link fails; only an existing authorized version can be linked |
| Withdrawal, disputes and accessibility | Withdrawal prevents new votes; no automatic vote deletion; reason and process audit retained; reviewer-conflict tests; escaping/CSRF/body limits; no-JS browser flow, keyboard and automated accessibility checks |
| Privacy and tenant isolation | Ordinary member cannot read individual ballots/eligibility roster; admin disclosure; active membership rechecked; cross-tenant queries, exports and foreign keys denied |
| Durability and evolution | Migration on fresh/existing module DB, restart before/after ballot/closure, transaction rollback, backup/restore, unique closure and race tests |

Run package race tests and vet, parser/validation fuzz targets, and browser tests against the isolated harness. Check actual source notices and module dependency advisories. Manual screen-reader, full core API compatibility, current-core service/store adapter, root ledger regression and final rollout approval remain separate gates; record unavailable tests as pending, not passed.

**Definition of done:** every adopted required behavior has implementation and evidence; a fresh audit agent reviews against this matrix and fixes findings. The feature can be complete as an isolated module only when its local requirements are met; that still does not authorize merging or activation. This research document is not an implementation-completion claim.
