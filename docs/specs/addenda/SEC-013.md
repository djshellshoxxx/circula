# Addendum SEC-013: operator break-glass trail

Status: implemented (partial, see "Not done"). Migration `0006_breakglass.sql`. Operator guide: [`docs/dev/break-glass.md`](../../dev/break-glass.md).
Spec text is unchanged: [`09-security-privacy.md`](../09-security-privacy.md) SEC-013, TA-5, DEC-014.

## Decisions

| # | Decision |
|---|---|
| 1 | A break-glass session is a row in `break_glass_sessions` (id, network, operator label, reason, opened, expires, closed, closed reason). The schema itself caps the length at 4 hours and allows only one close, nothing else may change, no delete. |
| 2 | TTL: default 4 h, hard maximum 4 h. A longer request is reduced to 4 h (clamp), not refused. Zero or negative selects the default. |
| 3 | A session is live while `now < expires_at` and it is not closed. At the exact expiry instant it is over. |
| 4 | Operator methods (`OpenBreakGlass`, `CloseBreakGlass`, `ListBreakGlassOperator`, `GrantBreakGlassAdmin`, `ExpireBreakGlass`) require a System actor. Not even a network administrator may call them. No HTTP route reaches them. |
| 5 | Opening, closing, expiring and role granting write the same audit event at platform scope (network id `''`) and at the network's scope, actor type `platform_operator`. The reason is in the event. Network administrators read the network copy in the audit log. |
| 6 | `RequireBreakGlass(ctx, netID)` is the gate for any operator action on a network's data or rights. It passes only with a live session of that network. |
| 7 | The only operator action that changes rights is `break-glass grant-admin`. It inserts a `break_glass_grants` row linked to the newest live session. The role is applied in `service.open` (`principal.go`) by joining the grant to its session at the current time, so it ends at expiry or close on the very next call. No job is needed for correctness, and the permanent `role_assignments` table is never touched. |
| 8 | Expired sessions are closed lazily (by every operator call) and by the job runner (`ExpireBreakGlass`, called from the expiry job). Closing records `closed_at = expires_at`, reason `expired`, and audits `break_glass.expired`. |
| 9 | Network administrators see the history on `/n/{slug}/admin/break-glass` (`ListBreakGlass`, administrator only, read only, per network). |

## Not done, owner decisions

1. Second approver (SEC-013 a). The spec asks for two staff. The CLI records one operator label and does not enforce a second person. Needs DEC-014 (technical gating or process only).
2. Notice to affected administrators within 24 h (SEC-013 c). The audit trail is readable by them; no push notice exists (no notification channel yet).
3. Existing operator CLI commands (`restore`, `admin create-operator`, `migrate`, direct database access) are not gated. The operator can still read the SQLite file (TA-5). The gate `RequireBreakGlass` is ready for any new operator command that touches a network, and the future password-reset command must call it.
4. A break-glass administrator can use all administrator powers, including granting permanent roles to other members (not to themselves). Every use is audited with the member's identity, not the operator's. Decide whether to narrow this.
5. The published operator access policy (release gate) is not written.
