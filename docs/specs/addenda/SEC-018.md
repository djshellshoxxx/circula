# Addendum SEC-018: erasure and anonymisation of a departed member

Status: implemented for departed members; owner decisions open (below). Migration `0007_erasure.sql`.
How to use and operate: [`docs/dev/erasure.md`](../../dev/erasure.md). Spec text is unchanged:
[`09-security-privacy.md`](../09-security-privacy.md) SEC-018, [`06-data-ledger-audit.md`](../06-data-ledger-audit.md) section 9 (DAT retention), DEC-020, RSK-011, RSK-023.

## Decisions

| # | Decision |
|---|---|
| 1 | `AnonymiseMember(actor, netID, memberID, reason)`: network administrator or System actor (operator CLI). `EraseMyData(actor, netID, reason)`: the departed member for themselves; reason optional. |
| 2 | Only members with status `departed`. Refused (blocked, with the list) while a proposed or disputed transaction, or an open / under review / posting pending dispute, involves the member. Refused if already anonymised. A balance does not block it. |
| 3 | Pseudonymisation, not deletion. The member id, account id, ledger entries, transaction rows, amounts, status events, dispute rows and the audit chain stay as they are. Display name becomes `Former member <last 8 chars of the member id>`. |
| 4 | Cleared: the member's listings (archived, title `Erased listing`, description empty), the memo (`transactions.note`) of transactions the member proposed, and the statement of disputes the member opened. |
| 5 | The person row (login, password hash, sessions, API tokens) is anonymised only when the person has no other non-departed membership anywhere: login becomes `erased-<person id>`, password hash becomes an unusable marker, all sessions are revoked, API tokens revoked and renamed, login throttle row removed. Otherwise the person is untouched. |
| 6 | The members table holds no bio, contact or profile fields today. If such fields are added, `ErasureRepo` is where they are cleared. MFA tables (SEC-007) do not exist yet and are not touched; the MFA feature must clear its own secrets in `erasePersonIfUnused`. |
| 7 | Irreversible. A reason is mandatory (administrator path), the action is audited as `member.anonymised` in the same unit, and recorded in `member_erasures` (append only, no personal data). Web and CLI require an explicit confirmation. |
| 8 | **Audit events are never edited.** Audit hashes cover the `reason` field. Reasons are administrator free text; they are not rewritten. Audit summaries hold no names (checked: no audit entry in the code puts a display name, login or contact into a summary). The erasure adds an event instead. The reason text of `member.anonymised`, and of earlier events such as the departure reason, may contain personal data if a person typed it; the UI says not to. |
| 9 | The transaction memo is NOT part of any hash (there is no transaction hash; `VerifyLedger` checks balances, entries and the audit chain), so it can be cleared. Administrator-written transaction `reason` (adjustments) is immutable by trigger and is kept. |
| 10 | Exports read live tables, so every export after erasure shows the anonymised name. Backups taken before erasure still hold the old data until the backup retention (SEC-028) ends. |

## Open owner decisions

1. **Memo retention and legal hold.** Memos are cleared by default because they are free text written by the member and no integrity check depends on them. If counsel decides that transaction memos are a legal record, add a legal-hold switch and keep them (the code change is one line in `anonymise`). Also decide whether memos written by the *counterparty* about the erased member (their own free text, not the member's data) stay; today they stay.
2. **Legal hold in general.** There is no hold flag: an administrator or operator can erase a member who is under a legal or dispute-related hold. Decide who may place a hold and add the check to `erasureBlockers`.
3. **Deferral record.** The spec asks that erasure of a member with an open dispute be deferred *and the deferral recorded*. Today the request is refused with the blocker list and nothing is written (a refusal writes no audit event). Departure itself is already blocked by a disputed trade, so the state is rare. Decide whether refusals should be audited or queued.
4. **Audit free text.** Reasons in the audit chain can hold personal data typed by administrators. Options: leave and warn (current), or redesign the hash to cover a reference to a separate, erasable reason store (changes SEC-019 and DAT-030; not done).
5. **Retention clock (DEC-020).** Nothing erases automatically at the end of a retention period. There is no scheduled job; erasure is an explicit action.
6. **Identified departed members elsewhere.** A person with only departed memberships has their login erased with the first erasure, while their other departed memberships keep their display names until erased individually (an administrator can do it). Decide if all memberships of the person should be erased together.
7. **Pre-erasure backups** keep the data until SEC-028 retention ends; the privacy information must say so.
