# SEC-007 addendum: second factor (TOTP) and recovery codes

Status: implemented (migration 0003). Spec text: `docs/specs/09-security-privacy.md` SEC-007. Operating guide: `docs/dev/mfa.md`.

## Decisions

- Method: TOTP, RFC 6238 over RFC 4226, HMAC-SHA1, 6 digits, 30 s step, stdlib only. Accepted window: current step +/- 1.
- Secret: 20 random bytes, base32. Provisioning via `otpauth://` URI (no QR image: no non-stdlib dependency; the setup key is shown as text, which also serves users who cannot scan).
- Replay: `person_mfa.last_step` is advanced with a conditional `UPDATE ... WHERE last_step < ?` in the same write unit as the login or confirmation; a step at or below it is refused. The enrolment-confirming code is burned the same way.
- Comparison: all three candidate steps are compared with `subtle.ConstantTimeCompare` without early exit.
- Secret at rest: AES-256-GCM sealed (`v1:` prefix, person id as AAD) when `Config.SecretKey` is set (cmd: `mfa-secret` / `mfa-secret-file`); otherwise base32 (`raw:`). The raw form is a known limit: a stolen database file yields working seeds. Prefer setting the key and encrypting backups. The seed is verify-only data: no API or page returns it after confirmation; during a pending enrolment (15 minutes) the same pending seed can be re-displayed to the same signed-in person.
- Recovery codes: 10 per enrolment, 10 base32 characters (50 bits) shown as `XXXXX-XXXXX`, single use, stored as SHA-256 over `label || person id || code` (high-entropy random codes; the person binding stops cross-person precomputation). Input is case and hyphen insensitive. Shown once. Replaced wholesale on regeneration; deleted on disable.
- Login: `Service.LoginStep` returns either a session token or, for MFA people, a 5-minute single-use challenge (SHA-256 stored in `mfa_challenges`). `CompleteMFA(challenge, code)` issues the session. The legacy `Login` signature is kept and, for MFA people, returns error code `mfa-required` and issues no session, so an adapter that was not updated cannot bypass the factor.
- Throttle: attempts are reserved up front in `login_throttle` under key `"\x1fmfa:" + personID` (5 failures, then 15 min doubling to 24 h; success resets). The key starts with a control character, which no valid login can contain, so a login string cannot lock or reset it. The same counter covers confirm, disable, regenerate and CompleteMFA. Never a permanent lock.
- Policy: platform setting `Config.RequireMFAForAdmins` (cmd key `require-mfa-admins`, default false), not a per-network policy field (policy versioning is out of scope here). When on, `requireAdmin` returns `forbidden` with message `mfa-enrolment-required` for an administrator with no enabled factor (a pending enrolment does not count). System actors are exempt. Non-admin operations by the same person still work, so they can reach the enrolment page. Platform operators act through the CLI (system actor) and are not covered. Reviewers are not required (DEC-007 default).
- Disable needs the current password and a TOTP or recovery code. Regenerate needs a TOTP code (not a recovery code).
- Audit actions (platform scope, no secrets): `mfa.enrol_begun`, `mfa.enabled`, `mfa.disabled`, `mfa.recovery_codes_regenerated`, `mfa.recovery_code_used` (carries remaining count). Each enabling, disabling, regeneration and recovery use also writes a security notice (SEC-012).
- Helper for account recovery work: `Service.VerifyAndConsumeRecoveryCode(tx, personID, code) (bool, error)`.

## Acceptance criteria to tests

| Criterion | Test |
|---|---|
| Admin with mandatory MFA cannot complete an admin action without a second factor | `service.TestRequireMFAForAdmins`, `TestRequireMFADefaultOff` |
| Used recovery code rejected on reuse | `service.TestRecoveryCodes`, `web.TestWebMFAEnrolAndLogin` |
| Secrets not retrievable after enrolment | `service.TestMFASecretsAndCodesNotStoredInClear`, `TestMFASecretSealedWithKey` |
| Enrolment and removal audited | `service.TestMFAEnrolFlow`, `TestDisableMFA` |
| RFC 6238 vectors, skew, replay | `service.TestTOTPRFC6238Vectors`, `TestMatchTOTPSkewAndReplay`, `TestCompleteMFA` |
| Throttle, not permanent | `service.TestMFAThrottle` |
| Races: one code, one challenge | `service.TestMFAConcurrentReplay`, `TestMFAConcurrentChallengeUse` |
| No bypass through legacy Login | `service.TestLoginWithoutMFAUnchangedAndLegacyLoginRefusesMFA` |
| Web flow, CSRF, login gating | `web.TestWebMFAEnrolAndLogin`, `TestWebMFAChallengeCSRFAndGet`, `TestWebSecurityNoticesAndDisable` |

## Known gaps

- No QR code and no WebAuthn. UX-053 (an option without transcription) is only partly met: the authenticator app removes manual transcription at login, but enrolment and recovery codes are typed.
- JSON API has no MFA endpoints or MFA login step; API tokens are unaffected by MFA (they are separately issued, revocable credentials).
- Changing a password does not touch MFA. Disabling MFA does not revoke other sessions.
- Challenges of a person are cleaned when that person next logs in; there is no global purge of expired `mfa_challenges` yet.
- Mandatory-for-admins is platform-wide, not per network.
