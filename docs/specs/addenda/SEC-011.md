# SEC-011 addendum: dual control for administrator adjustments

Status: implemented for adjustments (migration 0005). Write-offs and credit-limit changes are not yet covered (see Gaps).

## Decisions

| # | Decision |
|---|----------|
| D1 | Threshold-based, per network: `Policy.DualControlThreshold` (minor units, versioned with the policy, `0` = disabled, default `0`). An adjustment with `amount > threshold` needs a second administrator; `amount <= threshold` posts at once. Interprets DEC-013 "threshold-based". |
| D2 | A request is a row in `pending_adjustments` (status `pending`, `approved`, `rejected`, `expired`, `cancelled`). Nothing is posted and no balance moves until approval. |
| D3 | Approver: an active administrator who is not the proposer (SEC-010) and not the adjusted member (DOM-037). The proposer may cancel but not reject. |
| D4 | Everything is re-validated at approval: network active, target still active/suspended, proposer still an active administrator, amount and direction, and the member's limit (LED-5) through the normal posting path. |
| D5 | Requests expire after `Config.PendingAdjustmentTTL` (default 7 days). Expiry is lazy (any decision attempt closes an expired request and commits the closure) and by the job (`ExpirePendingAdjustments`, run from the existing expiry job). Expired requests post nothing. |
| D6 | Enabling or changing a non-zero threshold is refused (`dual_control_threshold` validation error) unless the network has at least two active administrators. If the second administrator later leaves, new above-threshold requests are refused (`invalid-transaction-state`) instead of parking undecidable requests; below-threshold adjustments still post. This is the DEC-013 single-administrator rule: the control is not offered, and the restriction is visible because the policy cannot hold the threshold. |
| D7 | Lowering or disabling the threshold is an ordinary audited policy change (`policy.changed` with before/after). It is not itself dual-controlled. |
| D8 | Old call `CreateAdjustment` keeps its signature and fails safe: above the threshold it returns error code `approval-required` (HTTP 403) and changes nothing. `CreateAdjustmentRequest` returns `AdjustResult{Tx, Pending}`. |
| D9 | Decisions are idempotent by state: the same decider repeating the same decision gets the original result; any other decision on a decided request is `invalid-transaction-state`. Concurrent approvals serialise on the write gate; the status update is conditional on `pending`, so exactly one posting happens. |

## Audit events (all in the network chain)

`adjustment.pending` (proposer, target, amount, direction, expiry), `adjustment.approved` (proposer and approver ids, transaction id), `adjustment.posted` (carries `request`, `proposer`, `approver`), `adjustment.rejected`, `adjustment.cancelled`, `adjustment.expired` (system actor).

## Gaps (not covered by this change)

- Write-offs (DOM-024 settle-to-zero on departure) and credit-limit changes still act on one administrator's say; the departure settlement calls the posting path directly. Extending dual control there needs its own request type.
- The "restriction shown to members in the change log" for single-administrator networks is satisfied only through the policy audit trail; no dedicated change-log entry is written.
- Administrator role revocation is not blocked while requests are pending; affected requests expire or are refused at approval (D4).
- The web policy form does not edit the threshold; set it through `PATCH /api/v1/admin/policy` (`dual_control_threshold_minor`). The form preserves the stored value on save.
- `pending_adjustments` is not part of the data export tables.


## Audit 2 hardening (SA2-01b, SA2-02)

Administrators can only enable or lower `dual_control_threshold`; loosening or disabling it requires the operator (`circula dual-control`). An administrator-initiated departure whose `settle_to_zero` settlement exceeds the threshold is refused with `approval-required`. See docs/audit/SECURITY-AUDIT-2.md.
