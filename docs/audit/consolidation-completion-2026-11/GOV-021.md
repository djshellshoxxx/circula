## Requirement and acceptance

> If no administrator can act, the platform operator MAY assist recovery only through a documented, dual-approved,
> audited process (SEC-013 break-glass) that verifies the requester's identity against the network's recorded members
> and notifies all members of the network. The platform operator MUST NOT appoint an administrator on its own authority
> and MUST NOT change balances as part of recovery.

## Owner gate (not decided by this change)

The implementation remains isolated. Its policy basis needs an owner decision before adoption:

1. **Permanent operator-mediated role versus SEC-013 decision 7.** The SEC-013 addendum (decision 7) says the only
   operator action that changes rights is the temporary, session-bound `break-glass grant-admin`, which never touches
   `role_assignments`. GOV-021 recovery, on a member's request and two approvals, creates a permanent role assignment.
   The owner must confirm that GOV-021 is an accepted second rights-changing operator path (and amend the addendum), or
   choose otherwise.
2. **Typed labels do not authenticate two staff.** Dual approval is two different typed `-operator` names; nothing
   proves they are two people. Whether stored, authenticated operator identities are required (DEC-014 family).
3. **Waiting or objection period.** Members are told at once, but two approvals can follow within minutes; whether a
   minimum wait or an objection step must precede the second approval.
4. **Expiry value.** 7 days is provisional (`domain.AdminRecoveryTTL`, and the schema maximum).

## Design

**Separate from ordinary break-glass.** The spec names SEC-013 break-glass, but A3-F02 records that a break-glass
administrator can make lasting changes, and DEC-014 leaves the ordinary break-glass second approver and scope open.
Recovery therefore uses its own table and its own CLI, needs no break-glass session, creates no break-glass grant and
does not change any break-glass code path. It shares the SEC-013 trail conventions instead: System actor, operator CLI
only, no HTTP route for operator actions (decision 4), documented reason, audit at platform and network scope with
actor type `platform_operator` (decision 5). DEC-014 is not resolved by this change.

**Requester and identity.** Only a member can start: `RequestAdminRecovery` (web `POST /n/{slug}/admin-recovery` with
CSRF and form idempotency key; API `POST /api/v1/admin-recovery/requests`, Idempotency-Key required, session cookie
only so a stolen API token cannot start an appointment). The requester is the nominee (no consent mechanism exists, so
no third-party nomination). Identity verification is the authenticated account resolved against the network's recorded
membership by the ordinary `service.open`: the member must be `active` (not pending, suspended, departed, or erased,
which implies departed), the network must be active (not closing or closed) and have no active administrator
(`lifecycle` / GOV-020), and, when `require-mfa-admins` is on, the member must have a second factor (the role they would
receive requires one). The same checks run again inside the write unit of each approval, so the request cannot outlive
the requester's eligibility.

**Operator identity and dual approval.** The build has no stored operator identity: `admin create-operator` creates an
ordinary person, and operator commands take a typed `-operator` label (break-glass, platform suspension). The strongest
available distinct identity is therefore the label. `domain.SameOperator` compares labels after trimming, collapsing
white space and Unicode case folding; the second approval is refused with `forbidden` when it matches the first. The
schema repeats the rule (`lower(trim(closed_by)) <> lower(trim(first_operator))` for an applied row). Each approval is a
separate CLI invocation and write unit with its own reason; the first only records.

**State machine and concurrency.** `requested -> approved -> applied`, and either open state to `refused`, `expired` or
`superseded`. Each transition is a compare-and-set on the current status (`ApproveAdminRecoveryFirst`,
`CloseAdminRecovery`) inside one SQLite write transaction that also holds the eligibility checks, the role grant and the
audit and notice rows; any failure rolls back all of it. Triggers forbid deletion, replacement, a non-`requested`
insert, changes of subject or times, any transition other than the listed ones, edits of the first approval after it is
recorded, an applied row without both approvals, and an applied row whose `role_assignment_id` is not the requester's own
live admin row in that network. Partial unique indexes allow one open request per member and network and one request
per role assignment.

**Effect.** The second approval calls `grantRoleTx` (extracted from `changeRole`, so `AssignRole` and recovery share the
single role-assignment path and the A3-01 notice to other administrators). It inserts one ordinary `role_assignments` row
with `granted_by = ''` (no granting member; the request links to the row). `AdminRequired` is derived from the active
administrator count, so the network leaves the read-only state at once. The appointee is a new administrator for A3-01
(the `NewAdminApprovalDelay` applies to their dual-control decisions). Other open requests of the network are closed as
`superseded`. Nothing in the ledger is read for writing; the recovery table has no reference to a ledger table.

**Expiry.** `domain.AdminRecoveryTTL` = 7 days (provisional), also the schema maximum. `ExpireAdminRecovery` runs in the
`serve` expiry job; an approval or refusal of an expired request closes and audits it (committed) and is refused, as in
dual-control adjustments. An open request reads `expired` from its expiry instant (`StatusAt`). The job walks expired
rows by ascending id (keyset, one write unit per batch of 100), so every backlog is reached.

**No bounded scans.** A member's own open request is found through the one-open-request partial unique index
(`GetOpenAdminRecovery`, an index probe checked by query plan), both for the duplicate check and for closing an
expired row before a new request; no page of other members' requests can hide it. Supersession walks the network's
open requests by keyset. Every list continues: the API lists use the signed `next_cursor`, the members' page has
"next" links for requests (`?after=`, 50 per page) and recorded steps (`?events_after=`, 100 per page), and the CLI list
pages with `-limit` and `-after`.

**Operator listing is audited access.** `circula admin-recovery list` reads requester names and membership dates, so
it requires `-operator` and `-reason` and writes `admin_recovery.listed` (actor `platform_operator`, reason in the
event, operator label and counts in the summary) at platform scope and in each network whose requests it showed, with
the shown requesters as subjects (SEC-013 a, b, decision 5). It shows only what a decision needs: id and network
(arguments), status and expiry, whether the network still has no administrator, whether the requester is still
eligible (a yes/no rather than the membership status), member id and display name (to match the out-of-band
confirmation), the membership date (takeover signal) and the first approval (who, when). No login, person id, contact
detail or balance is returned or displayed. Internally, the eligibility check reads the member row, including its
person id, to evaluate the second-factor requirement.

**Audit.** `admin_recovery.requested` (network scope, actor member, subject requester); `approved`, `applied`,
`refused` (platform and network scope, `platform_operator`, operator label in the summary, reason in the reason field);
`expired`, `superseded` (both scopes, actor `system`); `role.granted` for the appointee (network scope,
`platform_operator`). The network can read them: any non-pending member through `ListAdminRecoveryEvents` (page
*Administrator recovery*, `GET /api/v1/admin-recovery/events`) with the member-view reduction of FR-082 (no other actor
ids, reasons, hashes or subject lists; summaries keep `status`), the requester in their own audit view (subject), and the
appointed administrator in the full audit log. Operator reasons follow the existing audit-reason rule (no personal data;
documented in the runbook).

**Notice.** Every active and suspended member receives an inbox entry at request, first approval, application, refusal
and expiry (`notifyCurrentMembers`, pages of 500 over the full roster inside the step's write unit, the pattern of
cb25b41). The texts are fixed, neutral and carry no name, label or reason; they link to `/admin-recovery`. The service
cannot import the web catalogue (`internal/web/messages`; depguard and ARC-002), so notice texts follow the existing
FR-038 rule of fixed service texts; every string on the members' page is in the English catalogue (`admin_recovery.*`,
`notice.admin_recovery_link`).

**Erasure (SEC-018).** The table holds no member-written text; the requester is a member reference like other
member-linked rows and is kept after erasure. An erased member is departed, so an open request of theirs can only be
refused or expire. Names are shown from the live member record, which erasure replaces. Operator labels and reasons are
operator records (personal-data inventory updated).

**Layering.** Rules in `internal/service/admin_recovery.go` and `internal/domain/admin_recovery.go`; repository contract
`internal/repository/admin_recovery_iface.go`; SQLite `internal/store/sqlite_admin_recovery.go`; adapters
`internal/web/h_admin_recovery.go`, `internal/api/h_admin_recovery.go`, `cmd/circula/admin_recovery.go` hold no rule.
The API middleware now resolves the network before the session-only check, so a session-only network route of a
network the caller does not belong to reads as not-found (API-017); noNet routes are unaffected.

## Residual risk

1. One person typing two labels defeats dual approval; only organisational procedure (two named staff, ticket) and the
   member notices guard it.
2. Database-file access bypasses the service and most triggers (TA-5).
3. No waiting or objection period between request and appointment.
4. `service.AssignRole` still accepts a System actor (used by test fixtures); no operator command calls it, checked by
   `TestGOV021NoOperatorCommandAppointsDirectly`.
