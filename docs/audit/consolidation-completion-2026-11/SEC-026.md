### Semantics

- **Velocity.** After a trade proposal commits its own writes, the proposer's trade proposals (any later status) in the
  window ending now are counted. More than `velocity_signal_proposals` raises a `velocity` signal naming the proposer.
- **Reciprocal.** After a trade completes, the pair's completed trades in the window ending now are counted per
  direction. A pattern needs at least one trade in each direction; more than `reciprocal_signal_trades` in total raises
  a `reciprocal` signal naming the pair (ids ordered). Later disputes or reversals do not remove a completion.
- **One signal per window.** Counts slide with the triggering event; deduplication uses fixed periods of the window
  length aligned to the Unix epoch in UTC (`domain.SignalPeriodStart`; an instant on a boundary starts the next
  period). At most one signal per network, kind, member (or pair) and period is recorded. A burst that continues into
  the next period raises one more signal there. 30-day periods are epoch-aligned, not calendar months.
- **Never blocks.** Evaluation runs at the end of the command's unit inside a SQLite savepoint. Any failure (count,
  insert, audit, notice) rolls back only the savepoint; the proposal or trade commits as if signals were off, and the
  failure is passed to `Service.SetSignalFailureHandler` after the commit (serve logs a warning with network id, kind
  and error, no member data). A unit that rolls back for its own reasons reports nothing. The savepoint also trims the
  post-commit audit sink so a rolled-back audit event is never mirrored.
- **Concurrency.** `activity_signals_once` (UNIQUE on network, kind, member, other member, period) decides inside the
  write unit with `INSERT ... ON CONFLICT DO NOTHING`; there is no check-then-insert.
- **Recording.** Each new signal writes one `activity_signal.raised` audit event (system actor, no member subjects,
  summary: kind, observed, threshold, window minutes, period start) and one inbox notice (`review.activity_signal`) to
  every active administrator and dispute reviewer of the network except the members it names. The notice names no
  member and no count. Recipients are paged with the member cursor used for A3-01 (`eachActiveMember`), so
  administrators beyond the first 500 members are reached.
- **Visibility.** `Service.ListActivitySignals` requires the administrator or reviewer role (`requireDecider`: current
  effective roles, live break-glass grants, administrator MFA rule, active membership). Plain, suspended and departed
  members are refused (403); other networks' administrators and outsiders get not-found (404). Signals naming the
  reader are left out, so a member never sees a signal about themselves, also as a reviewer or administrator. The
  members concerned are not told and the audit event is absent from their own audit view.
- **Settings.** Five `Policy` fields: `activity_signals_enabled`, `velocity_signal_proposals`,
  `velocity_signal_window_minutes`, `reciprocal_signal_trades`, `reciprocal_signal_window_days`. Changes go through
  `UpdatePolicy`: validated bounds (GOV-005), one `policy.changed` audit event with before and after values (GOV-002), a
  new policy version with GOV-003 notice handling (not an adverse change, so no notice by default; an explicit notice
  schedules it). Evaluation uses the policy in force when the proposal is made or the trade completes (action-time
  rule, GOV-001); past events are not re-evaluated when a threshold changes. Older stored policy versions read with the
  defaults (on). The thresholds stay in bounds while signals are off.
- **Rules log.** Like `dual_control_threshold`, the five signal keys are left out of the policy change log
  (`hideReviewOnlyKeys`) so the thresholds do not teach members how to stay below them. Administrators see them on the
  policy page and the audit log. Every change to them sends `review.activity_signal_settings` to the other active
  administrators and reviewers, so one administrator cannot quietly switch signals off or loosen them.
- **Erasure (SEC-018).** Signal rows hold member ids and counts only and stay unchanged, like `audit_subjects` and
  `challenges`; the reviewer page then shows `Former member ...`. The personal-data inventory lists the table under
  "Other columns"; `docs/dev/erasure.md` lists it as unchanged.

### Migration 0020

Additive only. New table `activity_signals` (CHECKs: kind, observed > threshold > 0, velocity has no second member,
reciprocal pair ordered, raise time inside its period; composite foreign keys to `members`); unique index
`activity_signals_once`; queue index; trade indexes `tx_velocity` and `tx_pair_completed`. Append-only guards: UPDATE and
DELETE abort, an existing id aborts, and an existing deduplication key turns any insert (REPLACE included) into a no-op
(`RAISE(IGNORE)`). `scripts/check_migrations.py` now protects the table. Upgrade from v18 keeps every existing row
(`TestSEC026SignalMigrationIsAdditive`).

## Provisional defaults (owner to confirm)

[12](../../specs/12-quality-test-plan.md) sets no recommended defaults, and
[09 open question 10](../../specs/09-security-privacy.md#9-open-questions) ("whether the threshold for velocity signals is
a product decision or a test-engineering default") is open. The values below are **provisional, owner to confirm**.
They are chosen to rarely signal ordinary use; a network can change them.

| Setting | Provisional default | Bounds |
|---|---|---|
| `activity_signals_enabled` | on | on / off |
| `velocity_signal_proposals` | more than 20 proposals | 1 to 1000 |
| `velocity_signal_window_minutes` | 60 | 1 to 10080 (one week) |
| `reciprocal_signal_trades` | more than 10 completed trades, both directions | 1 to 1000 |
| `reciprocal_signal_window_days` | 30 | 1 to 365 |

## Known gaps and caveats

- No browser end-to-end test was run (local Chromium sandbox); markup follows the existing accessible admin pages and
  `TestPageStructure` covers the new page.
- Signals have no "reviewed" or "dismissed" state: they are append-only prompts and stay listed. A workflow is not in
  SEC-026.
- In a network whose only administrator and reviewers are the members a signal names, nobody can see it.
- Signals are not part of network exports (not required; listed as not exported in the inventory).
- Changing a window length mid-period can create a second signal for an overlapping period of the new length.
- The savepoint relies on SQLite; a future PostgreSQL store must implement `Savepoint` with the same semantics.
- The HTML page pages with the raw `after` id, like the other HTML queues; the JSON API uses the signed cursor.
- GOV-002 says every policy change is shown to members; the signal keys (like the dual-control threshold) are not. A
  change touching only signal settings appears in the members' log as a version with no visible changes.
